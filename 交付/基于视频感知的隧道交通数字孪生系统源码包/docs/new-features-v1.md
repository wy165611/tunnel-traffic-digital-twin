# 隧道功能 v1：事件、告警、服务水平、实时流与低照度增强

本文逐项说明 `feat/tunnel-features-v1` 新增功能的原理、配置项、导出字段与限制。所有速度相关输出仍然遵守原有原则：**没有真实道路尺寸时保持关闭，不生成虚构速度、密度或服务水平**。

## 1. 事件检测扩展

### 1.1 超速与低速

- 超速：`speed > speeding_kmh`（若本机位场景设置了 `speed_limit_kmh`，优先使用该限速值）。
- 低速：`stop_speed < speed < slow_speed_kmh`，低于停车阈值时只进入异常停车规则，避免重复报警。
- 速度来自已保存四点标定和 Homography 世界坐标；未标定时车辆速度为 `null`，两条规则自动静默。界面提示“需速度标定”。

配置（`config.yaml → events`，也可在“分析参数”修改）：

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `speeding_enabled` / `speeding_kmh` | `true` / `80` | 超速开关与默认阈值 |
| `slow_speed_enabled` / `slow_speed_kmh` | `true` / `20` | 低速开关与阈值 |
| `cooldown_seconds` | `5` | 同一车辆同一机器事件的生成冷却；与告警推送冷却相互独立 |

本机位限速保存在场景 `speed_limit_kmh` 中，随 `run.json`、摄像头模板保存；分析参数中的超速阈值作为未设置本机位限速时的默认值。

### 1.2 违规变道（实线禁变道）

- 基于现有车道归属：车辆从车道 A 进入车道 B 后，若在新车道持续达到 `lane_change_seconds`，触发 `ILLEGAL LANE CHANGE`。
- 每车道新增 `solid_line`（默认 `true`）。只有当前车道为实线时才报警；虚线车道允许变道。
- 规则不依赖速度标定，但需要绘制车道；只在车辆被观测到的帧更新。
- 同一段行程对同一次变道只报告一次；再次换道会重新计时。

### 1.3 跟车过近

- 同一车道内，取本车沿车道方向前方最近车辆，车头时距近似为
  `headway = 前后车世界坐标在车道方向上的间距 / 本车速度 (m/s)`。
- `headway < tailgating_headway_seconds`（默认 2 秒）触发 `CLOSE FOLLOWING`。
- 需速度标定与车道方向；停止车辆不参与，避免停车排队时全部报警。
- 使用车辆中心点间距，未减去车身长度，属于偏保守的近似；不同车型长度差异未建模。

### 1.4 排队与拥堵

- 标定后：车道内 `speed < queue_speed_kmh`（默认 10 km/h）的观测车辆计入排队；排队长度取这些车辆世界坐标在车道方向上的投影跨度，单位米。
- 未标定：没有真实速度，使用跟踪器像素速度 `pixel_speed < queue_pixel_speed`（默认 5 px/s）估计排队车辆数，长度不可用；界面标注“图像估计”。
- 拥堵等级综合排队比例与车道均速：`free/畅通`、`slow/缓行`、`congested/拥堵`、`severe/严重拥堵`。未标定时仅按排队比例估计。
- 排队长度是“排队车辆中心点跨度”，不是逐车长度累加，也不是完整隧道排队长度；相机只覆盖有限路段。

### 1.5 行人 / 非机动车闯入

- 只有所选模型实际输出 `person` / `bicycle` 时才可能触发：
  - COCO YOLO11n：加入 person、bicycle 类别；
  - COCO SSD MobileNetV3：加入 person、bicycle 类别；
  - VisDrone YOLO11n：无上述类别，界面明确显示“当前模型不支持 person / bicycle 类别”。
- 事件 `PEDESTRIAN INTRUSION` / `NON MOTOR INTRUSION` 不要求速度标定，只需要模型检出、跟踪确认且位于视频分析区域。
- 行人和非机动车不计入机动车流量、车道密度、速度统计和排队统计，避免污染交通指标。
- 模型类别能力是静态配置声明，不代表该机位一定能检出；远距离、遮挡和夜间效果需实测。

## 2. 告警推送

### 2.1 前端弹窗与提示音

- 新的机器事件通过 WebSocket 到达后，右下角显示最多 3 条弹窗，8 秒自动关闭，也可手动关闭。
- 提示音使用 Web Audio 合成蜂鸣，无需外部音频文件；事件记录面板提供“提示音开/关”，偏好保存在 `localStorage`。
- 按“车辆 ID + 事件类型”默认 10 秒冷却去重；同一车辆同类事件在冷却窗口内不重复弹窗和播放提示音。不同车辆或不同事件类型不受影响。
- 冷却值来自 `alerts.cooldown_seconds` 并随状态快照下发。首批补充要求曾建议 30 秒，第二批补充要求改为默认 10 秒；本实现采用**较新的 10 秒**。

### 2.2 Webhook

```yaml
alerts:
  webhook_enabled: false        # 默认关闭
  webhook_url: ''              # 仅接受 http/https
  webhook_timeout_seconds: 3.0 # 单次请求超时
  webhook_retries: 2           # 首次失败后最多重试 2 次（共 3 次尝试）
  cooldown_seconds: 10.0       # 同车同事件推送冷却
  webhook_headers: {}          # 自定义请求头（如网关 Token），不写入日志
  webhook_hmac_secret: ''      # 非空时启用 HMAC-SHA256 签名
  webhook_hmac_header: X-Twin-Signature
```

- 事件保存证据后调用 `WebhookNotifier.notify`；发送在独立 daemon 线程中执行，视频处理主循环不等待网络。
- POST JSON：`type=traffic_event`、`run_id`、`video_id`、`sent_at` 和完整 `event`（含事件 ID、视频时间、车辆 ID、类型、车道、速度）。
- 鉴权：`webhook_headers` 中的自定义 Header 原样附加（保留 `Content-Type`、`Content-Length`、`Host` 等保留头不可覆盖，含换行的非法值被忽略）。设置 `webhook_hmac_secret` 后额外发送 `X-Twin-Timestamp`（Unix 秒）和签名头，签名为 `sha256=HMAC_SHA256(secret, "<timestamp>.<原始 JSON body>")`；每次重试重新生成时间戳与签名。
- 投递日志：每次实际投递（成功或失败）记录事件 ID、尝试次数、HTTP 状态码或错误类型，`GET /api/webhook-log?limit&offset&status=success|failed` 可查询；日志为进程内环形缓冲（最多 500 条），不记录 URL、密钥或自定义 Header 值，进程重启后清空。
- 所有异常（DNS、超时、连接错误）被捕获并忽略，不影响分析、CSV 和事件证据；重试间隔为 0.2、0.4 秒，仍失败则放弃本次推送。
- 接收端校验：先比较 `X-Twin-Timestamp` 与本地时间，偏差超过 5 分钟直接拒收；再用同一密钥对 `"<timestamp>.<原始 body>"` 重算签名，并拒绝重复时间戳。发送端只负责生成时间戳与签名，不实现接收端验签与防重放逻辑。

## 3. 虚拟线圈、时间占有率与服务水平

### 3.1 虚拟线圈

- 每绘制一条车道，后端自动生成一个细长凸四边形线圈：
  1. 用 `cv2.minAreaRect` 求车道最小外接矩形；
  2. 沿长边取 ±18%，沿短边取 ±55%，形成车道中央的检测带；
  3. 若角点因不规则凸多边形落到车道外，则退回中心缩放的凸多边形。
- 线圈可调：场景 JSON 的 `lanes[].loop` 可提供自定义凸多边形，系统优先使用；非法或非凸线圈在保存时报错。
- 线圈随场景保存，并随固定机位模板一起保存/应用；前端在视频画面上以虚线叠加。
- 分析参数提供“启用虚拟线圈时间占有率”，对应 `traffic.time_occupancy_enabled`，默认开启。关闭时仍显示线圈，但占有率不可用。

### 3.2 时间占有率

- 对每个线圈，按相邻处理帧的视频时间差累积覆盖秒数；当前帧有观测车辆底部中心点落入线圈时，该区间记为占用。预测帧不参与。
- `occupancy = 占用秒数 / 已覆盖秒数 × 100%`，为运行段累计值，不是信号周期意义上的本地控制器占有率。
- 车辆中心点落入线圈是简化判据，没有按车身长度计算线圈被压占的精确时间；跟踪抖动和检测间隔会影响结果。
- 未绘制车道、车辆不经过线圈或分析时间过短时，值可能为空或波动明显。

### 3.3 服务水平 A–F

- 每车道密度 = 该车道已标定、已观测车辆数 ÷ 车道可见长度（km）。车道长度由车道多边形标定点沿车道方向的世界坐标投影跨度得到。
- 密度分级参考 HCM 自由流密度区间：A ≤ 7、B ≤ 11、C ≤ 16、D ≤ 22、E ≤ 28、F > 28 辆/(km·车道)。
- 再结合观测均速降级：均速 < 30 km/h 时至少为 D，< 15 km/h 时至少为 E。整体服务水平用全部标定车辆数 ÷（道路长度 × 车道数）计算整体密度后按同样规则给出。
- 未标定时密度和服务水平不可用，界面显示“未标定”，不会用图像像素伪造密度。
- 这是面向演示的工程近似，不是经过标定的 HCM 或通行能力评价；短路段车辆数少、车道长度短会使密度跳动明显。摄像头只覆盖局部路段，不能外推为整条隧道服务水平。

### 3.4 导出与报告

- `traffic_statistics.csv` 新增 `density_per_lane`、`occupancy`、`level_of_service`、`service_level_label`、排队与拥堵字段。
- `lane_statistics.csv` 新增每窗口的 `density`、`flow_per_hour`、`occupancy`、`level_of_service`、`service_level_label`、排队与拥堵字段。
- JSON 报告新增 `service_level`（末次占有率、A–F、排队车辆/长度、拥堵标签）；HTML 报告在概览事实和分车道表加入占有率、服务水平和排队列。旧 CSV 缺少这些列时显示“不可用”，不补造数值。

## 4. 实时视频流接入

### 4.1 配置与状态

- 页面“导入交通视频”弹窗新增流地址输入，支持 `rtsp://`、`rtsps://`、`http://`、`https://`，调用 `POST /api/video/stream`。其他协议（包括 `file://`）直接拒绝。
- 成功连接后状态栏显示“实时流 · 已连接”；与录播一样可开始/暂停/重新分析。流地址只显示主机名，不在界面泄露路径或账号密码。
- 读取失败后状态变为 `reconnecting`，页面显示“已断开 · 正在重连（第 N 次）”，主状态标签显示“实时流重连中”。重连成功后自动恢复为“已连接”，同一统计段继续写入。
- 无可用流时只在当前连接报错，导入弹窗关闭后本地视频列表仍可选择和播放，本地功能不受影响。

### 4.2 指数退避与时间戳

- 重试等待序列为 1、2、4、8、16 秒，上限 30 秒；每次失败后重新创建 `VideoCapture` 并重读帧。
- 重连后新流的解码时间可能从 0 重新开始；读取器记录断线前最后时间，把恢复后的第一帧映射为“最后时间 + 1 帧”，保持 WebSocket 时间戳单调，图表和统计段不会倒退。
- 直播模式 `seek` 在前后端均被禁止；前端拖动条禁用并显示“LIVE”。
- 重连使用原显示尺寸缩放新帧以保持坐标空间一致；检测到新流宽高变化时置 `video.resolution_changed=true` 并记录旧/新尺寸，原标定立即失效（测速、跟车时距、排队米数、密度、服务水平停用），前端提示重新标定；重新保存标定后清除标记。

### 4.3 限制

- RTSP 默认优先 `rtsp_transport=tcp`，并通过 `CAP_PROP_OPEN_TIMEOUT_MSEC / CAP_PROP_READ_TIMEOUT_MSEC` 限制打开与读取阻塞（`video.stream_open_timeout_seconds / stream_read_timeout_seconds`，默认 8/10 秒）；仍没有 RTSP 认证重试、码流切换、录像回放或断流持久化队列。
- 未在真实 RTSP 设备/长时间弱网环境完成上线验收；测试使用确定性假视频源验证退避、状态、TCP/超时参数和时间戳连续性。
- OpenCV/FFmpeg 对超时参数的支持取决于构建版本；旧版本会退化为普通 `VideoCapture`，打开阶段仍可能较慢。

## 5. 隧道低照度 / 明暗适应预处理

### 5.1 原理与配置

- 默认关闭。开启后对每一帧先做 LAB 亮度通道 CLAHE（自适应直方图均衡），再对 BGR 结果应用 Gamma 查找表（Gamma > 1 提亮）。
- 处理发生在检测、JPEG 显示和事件截图之前，因此检测器、孪生/视频和证据看到同一增强帧。
- 分析参数新增开关、`low_light_clahe_clip`（1–10）和 `low_light_gamma`（0.5–3）。对应 `config.yaml → preprocessing.low_light_enabled / clahe_clip_limit / gamma`。切换参数会重建统计段，旧 CSV 保留。

### 5.2 帧率实测

测量环境：Linux x64、8 vCPU（Intel Xeon）、Python 3.13.5、OpenCV 4.14.0、NumPy 2.5.2、CPU、960×540 合成低照度画面。结果是一次本机基准，不是所有硬件的保证：

| 场景 | 关闭增强 | 开启增强 |
| --- | --- | --- |
| 仅增强模块，300 帧，取总耗时换算 | 直通（无额外计算） | 403.6 FPS（约 2.48 ms/帧） |
| 完整处理循环 + 桩检测器，120 帧，3 次中位数 | 903.2 FPS | 181.1 FPS |

完整循环包含跟踪、指标、JPEG 编码和 CSV 写入；桩检测器不包含真实模型推理。实际部署中 YOLO/SSD 推理通常占主要耗时，增强带来的相对帧率下降会小于上表。界面“处理 FPS”为最近 30 帧算法吞吐，可用于现场对比开启前后的变化；每个机位的光照、分辨率和 CPU 不同，应现场记录。

### 5.3 限制

- CLAHE + Gamma 是通用对比度增强，不做去雾、去噪、运动模糊恢复或真正的低照度成像模型。
- 增强会放大噪点和压缩伪影，可能提高误检；默认关闭，必须用目标隧道素材对比开启前后的检测和报警效果。
- 不做逐帧亮度自动判断，也不会自动切换参数。

## 暂不做与后续计划

本版明确不实现：

1. **3D 数字孪生**：仍为二维道路平面与同帧车辆；3D 需要相机外参、车辆三维尺寸和渲染管线。
2. **多摄像头接力**：当前是单分析会话；跨机位 ID 保持、时间同步和轨迹拼接需要额外基础设施。
3. **抛洒物分类与烟火识别**：已提供基于虚拟线圈前景占用的“路面异物”启发式（只判断异常占用，不区分异物类别）；真正的抛洒物分类与烟火识别需要专门检测模型和训练/验证数据。

后续可按以下顺序推进：真实隧道多光照数据采集与标定 → 事件阈值现场校准 → RTSP 长稳测试与鉴权 → 专门模型评估 → 3D/多机位。
